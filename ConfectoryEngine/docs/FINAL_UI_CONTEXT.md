# Confectory 최근 UI 및 컨텍스트 구조 수정안

이 문서는 Codex 재연결 과정에서 발견된 문제부터 이후 실제 Confectory를 실행하며 확인하고 확정한 변경사항을 정리한다.

이미 구현된 항목은 다시 수정할 필요 없으며, 아직 반영되지 않은 항목만 적용한다.

---

## 1. Codex 연결 UX 정리

현재 Codex 연결 복구 과정에서 다음과 같은 흐름이 발생했다.

- 기존 Codex 연결이 풀려 있음
- 다시 연결하려 하자 Codex가 없는 것처럼 표시됨
- 동의 항목을 발견하고 체크한 뒤 연결했으나 반응 없음
- Claude로 이동했다가 다시 Codex로 돌아옴
- 다시 동의 후 연결하자 모든 버튼이 비활성화됨
- 취소 후 다시 연결하기
- 동의 후 연결
- 최종적으로 성공

문제는 연결 성공 여부보다 **현재 어떤 상태인지 사용자가 추론해야 한다는 것**이다.

### 수정 원칙

연결 과정의 내부 상태 머신은 숨겨도 되지만 다음 정보는 항상 표시한다.

- 사용 가능 여부
- 권한 동의 여부
- 인증 대기 여부
- 연결 중 여부
- 연결 성공 여부
- 연결 실패 여부 및 실패 이유

예:

```text
Codex
✓ 사용 가능
✓ 권한 동의 완료
● 연결 중...
```

연결 중 버튼을 비활성화한다면 반드시 `연결 중...`과 같이 이유를 표시한다.

실패한 경우:

```text
연결 실패
인증 세션이 만료되었습니다.

[다시 시도] [취소]
```

처럼 다음 행동을 명확하게 제공한다.

# 2. 메인 페이지의 기존 프로젝트 불러오기

현재 새 프로젝트 생성 기능은 있으나 **기존 프로젝트 불러오기 진입점이 없다.**

그 결과 기존 Golemancer 프로젝트가 존재함에도 Confectory에서 프로젝트에 진입할 방법이 없어졌다.

별도의 큰 슬롯을 하나 더 만드는 대신, 기존 첫 번째 `새 프로젝트` 슬롯을 **프로젝트 추가 슬롯**으로 확장한다.

예:

```text
┌────────────────────────────┐
│                            │
│  ┌──────────┐ ┌──────────┐ │
│  │    +     │ │    ↗     │ │
│  │새 프로젝트│ │ 불러오기 │ │
│  └──────────┘ └──────────┘ │
│                            │
└────────────────────────────┘
```

즉 첫 번째 슬롯의 의미는:

```text
기존:
새 프로젝트

변경:
프로젝트 추가
├ 새 프로젝트
└ 기존 프로젝트 불러오기
```

기존 프로젝트를 선택하면 Confectory 프로젝트인지 검증한 뒤 프로젝트 목록에 등록한다.

---

# 3. 최소 프로젝트 회귀 테스트

대규모 리팩토링 중에도 다음 흐름은 항상 동작해야 한다.

```text
Confectory 실행
→ 기존 Golemancer 프로젝트 불러오기/선택
→ 프로젝트 진입
→ ▶ 실행
```

Golemancer는 Confectory의 실제 사용 프로젝트이므로 이 흐름을 최소 생존 테스트로 사용할 수 있다.

---

# 4. 새 프로젝트 생성창 UI

실제 실행 과정에서 몇 가지 UI 문제가 확인되었다.

## 4-1. 프로젝트 설명 입력 필드

`AI에게 프로젝트 설명` 아래에 큰 멀티라인 입력 필드가 존재하지만 배경과 거의 구분되지 않아 입력 필드가 있다는 사실조차 알아보기 어렵다.

입력 필드는 최소한 다음 시각적 구분을 갖는다.

- 입력 영역 배경 구분
- 테두리
- Focus 상태 표시
- 필요하다면 Placeholder

필드 이름은 기존처럼 프로젝트 설명임을 알 수 있는 단순한 표현을 사용한다.

---

## 4-2. 프로젝트 이름 필수 표시

프로젝트 이름을 입력하지 않은 상태에서 나머지 항목을 모두 입력하면 `만들기`가 동작하지 않지만 그 이유를 알기 어렵다.

프로젝트 이름이 필수라면 이를 명확하게 표시한다.

예:

```text
프로젝트 이름 *
[                ]
```

생성 시 이름이 없다면 해당 필드에 오류를 표시하고 포커스를 이동한다.

사용자가 `왜 생성이 안 되지?`를 추론하게 하지 않는다.

---

# 5. 버튼 Pressed 상태

일부 버튼은 마우스를 호버하는 순간 시각 효과가 글자를 덮어 버튼 이름을 읽을 수 없게 된다.

Hovered 상태에서도 버튼의 내용은 항상 읽을 수 있어야 한다.

Hovered 표현 방법은 이후 조정 가능하지만 예를 들면:

- 글자를 약간 어둡게 함
- 테두리를 강조함
- 배경 밝기를 조절함

등을 사용할 수 있다.

---

# 6. 좌측 AI 관리 사이드바

기존 사이드바는 원형 아이콘 두 개가 겨우 들어가는 폭이었으며, 레이아웃 변경 이후 아이콘이 오른쪽으로 밀리면서 잘리는 현상까지 발생했다.

사이드바를 억지로 좁게 유지하지 않는다.

## 기본 방향

- 사이드바 폭을 현재보다 넉넉하게 확보
- 필요 없을 때 접을 수 있도록 함
- 수동 X 좌표보다는 컨테이너 정렬을 우선
- 펼친 상태에서는 정보 표현에 필요한 공간을 확보

---

## 6-1. 사이드바의 사용자 노출 항목

기본적으로 다음 세 영역을 가진다.

```text
Agent

Helper

Player (현재 접속자 수)
```

Worker는 사용자 목록에서 제거한다.

기존의:

```text
Worker 추가
YogiBox
```

버튼도 일반 사용자 UI에서 제거한다.

Worker는 Helper가 내부적으로 생성하고 관리하는 실행 자원이다.

YogiBox는 후술한다.

---

## 6-2. Helper의 Worker 상태 표시

사용자가 개별 Worker를 기억하거나 찾아갈 필요는 없다.

Helper에 Hover하면 나타나는 프로필 하단에 다음 정도만 표시한다.

```text
작업자 6

● ● ● ○ ● ●
```

점들은 Worker의 신원을 나타내는 것이 아니라 상태를 나타낸다.

예:

- 작업 중
- 대기
- 완료 직후
- 충돌/협의 중
- 오류/중단

등.

사용자가 특정 상태가 궁금하면 해당 Helper에게 물어본다.

예:

```text
"빨간 거 뭐야?"
```

Helper가 내부 Task/Worker 상태를 조회해 설명한다.

---

## 6-3. 표시 줄 수

Helper나 Agent는 일반적으로 많지 않지만, 멀티플레이에서는 Player가 많아질 수 있다.

따라서 한 줄로 강제하기보다 **최대 두 줄 정도를 기본 표현 공간으로 유지**한다.

초과 인원은:

```text
+17
999+
```

등으로 요약할 수 있다.

# 7. 하단 프로젝트 패널

기존 프로젝트 채팅은 좌측 사이드바 하단에 매우 작은 영역으로 존재해 실제 대화 용도로 사용하기 어렵다.

또 과거에 존재하던 로그 영역의 역할도 다시 필요하다.

따라서 프로젝트 화면 하단에 넓은 공통 패널을 둔다.

구조:

```text
[ 프로젝트 채팅 ] [ 로그 ]

현재 탭 내용

──────────────────────── (채팅 시)
입력 영역
                    [보내기]
──────────────────────── (채팅 시)
최근 로그 한 줄
```

## 원칙

채팅과 로그를 하나의 스트림에 섞지 않는다.

같은 하단 패널을 공유하되:

```text
채팅 탭
로그 탭
```

으로 구분한다.

채팅 입력 영역 아래에는 **가장 최근의 의미 있는 로그 한 줄**을 표시해, 채팅을 보고 있어도 시스템 상태를 놓치지 않도록 한다.

예:

```text
최근 로그  ✓ Build completed
```

또는:

```text
최근 로그  ✕ ProjectPack load failed
```

세부 로그는 `로그` 탭에서 확인한다.

# 8. 프로젝트 화면의 버튼 구조

프로젝트 화면의 역할을 다음처럼 분리한다.

```text
좌상단
≡ 프로젝트 메뉴

우하단
신문고 / 실행 / 프로젝트 내부 탐색
```

---

# 9. 좌상단 햄버거 메뉴

햄버거 메뉴는 프로젝트 내부 탐색 버튼으로 사용하지 않는다.

햄버거의 실제 역할은 **현재 프로젝트 자체의 관리 메뉴**다.

프로젝트 이름 옆에 배치한다.

예:

```text
(≡) The Golemancer's Factory
```

메뉴에는 다음과 같은 항목이 들어갈 수 있다.

```text
프로젝트 정보
프로젝트 설정
프로젝트 폴더 열기
----------------
프로젝트 나가기
```

특히 현재 구현에는 `프로젝트 나가기`가 없으므로 이 메뉴가 해당 진입점을 담당한다.

---

# 10. 프로젝트 내부 탐색 버튼

기존 우하단 햄버거 버튼은 `2×2 Grid` 형태의 아이콘으로 변경한다.

예:

```text
■ □
□ □
```

또는 이에 대응하는 단순 Grid 아이콘.

의미:

```text
프로젝트 내부의 여러 작업 공간 / 개념 / 기능 탐색
```

즉:

```text
≡ = 프로젝트 자체 관리
▦ = 프로젝트 내부 탐색
```

으로 역할을 분리한다.

---

## 10-1. Grid 메뉴 전개 방식

Grid 버튼을 누르면 일반적인 Context Menu가 뜨는 대신, 버튼 위쪽으로 **길고 모서리가 둥근 메뉴 바**가 펼쳐진다.

예:

```text
╭──────────────────╮
│ 프로젝트 개요     │
│ 개념 탐색         │
│ 최근 작업         │
│ ...              │
╰──────────────────╯
         ▦
```

필요한 경우 하위 메뉴는 왼쪽 방향으로 추가 확장할 수 있다.

확장하다 공간이 부족한 경우 다시 오른쪽을 향해 돌아오며 핑퐁으로 진행할 수 있다.

---

# 11. 우하단 프로젝트 액션 영역

우하단의 주요 액션 버튼은 동일한 계열의 원형 버튼으로 통일한다.

기본:

```text
(🗃️)  (▶)  (▦)
```

향후 다른 프로젝트 액션이 추가되더라도 왼쪽으로 이어 붙일 수 있다.

---

# 12. 신문고 UI

신문고는 텍스트 `신문고` 버튼이 아니라 다른 프로젝트 액션과 동일한 **원형 아이콘 버튼**으로 변경한다.

아이콘은 우편함/편지함 계열을 사용할 수 있다.

## 상태 표현

신문고가 비어 있으면 빈 편지함.

미해결 항목이 존재하면 편지가 꽂혀 있는 모습으로 표현할 수 있다.

배지는 기존 신문고 명세를 유지한다.

```text
배지 숫자
= 현재 미해결 항목 수

배지 배경색
= 미해결 항목 중 가장 높은 경고 단계의 색
```

따라서:

```text
[1] 빨강
```

은 하나뿐이어도 긴급한 문제이며,

```text
[99+] 낮은 단계 색
```

은 많은 항목이 쌓여 있어도 최고 긴급도는 낮다는 의미다.

해결된 항목은 숫자에 포함되지 않는다.

---

# 13. YogiBox 보관 메뉴 제거

기존 구현에는 `YogiBox` 버튼과 별도의 보관된 YogiBox 개념이 존재했다.

이 구조는 제거한다.

YogiBox는 프로젝트에 영구 보관되는 객체나 별도 관리 목록이 아니다.

YogiBox는:

```text
Yogi 작성
→ 확인/수정
→ 설명
→ 봉인
→ 전달
```

을 위한 **일시적인 컨텍스트 전달 패키지**다.

따라서 좌측 AI 관리의 `YogiBox` 메뉴 버튼도 제거한다.

단, 채팅이나 신문고 등에 전달된 YogiBox는 해당 기록의 첨부물로 다시 볼 수 있다.

별도의 `YogiBox 보관함`은 만들지 않는다.

---

# 14. YogiBox 작성 UI

Yogi 기능으로 처음 대상을 담으면 화면 하단에 현재 작성 중인 YogiBox 영역이 나타난다.

예:

```text
┌────────────────────────────── × ┐
│ [Yogi A ×] [Yogi B ×]          │
│                                │
│ 설명                           │
│ [............................] │
│                    [봉인하기]   │
└────────────────────────────────┘
```

## 담긴 Yogi

각 Yogi는 전달받는 쪽에서 보게 될 형태와 동일하거나 유사하게 표현한다.

즉 해당 요소의:

- 생김새
- 아이콘
- 버튼 형태

등을 유지한다.

사용자가 Yogi를 클릭하면 해당 원본 객체나 위치로 이동할 수 있어야 한다.

이를 통해:

```text
"내가 제대로 이걸 넣은 게 맞나?"
```

를 바로 확인할 수 있다.

각 Yogi 오른쪽 위의 `×`는 **그 Yogi 하나만 삭제**한다.

---

## 14-1. YogiBox 전체 삭제

펼쳐진 YogiBox 자체에도 오른쪽 위 `×`가 존재한다.

이 `×`는 YogiBox 전체를 폐기한다.

삭제는 명시적인 `×` 동작을 통해 처리한다.

---

# 15. YogiBox 봉인 상태

`봉인하기`를 누르면 YogiBox는 작은 드래그 가능한 버튼으로 축소된다.

예:

```text
[ 📦 × ]
```

봉인된 YogiBox는:

- 프로젝트 채팅에 드래그
- 왼쪽 AI 관리의 Helper에게 드래그
- 다른 Player에게 드래그

등으로 전달할 수 있다.

봉인 상태에서도 오른쪽 위 `×`로 YogiBox 전체를 삭제할 수 있다.

더블클릭하면 다시 펼쳐 편집한다.

---

## 15-1. 새로운 Yogi 추가

봉인된 YogiBox가 존재하는 상태에서 새로운 Yogi를 추가하면:

```text
봉인 상태
↓
새 Yogi 추가
↓
자동 봉인 해제
↓
기존 Yogi + 새 Yogi가 들어 있는 작성 영역 표시
```

로 동작한다.

즉 YogiBox는 `sealed / unsealed` 상태를 오갈 수 있다.

---

# 16. 현재 YogiBox 구현 버그

실제 테스트에서 다음 문제가 발생했다.

1. Yogi를 추가할 때마다 UI의 `YogiBox` 이름 뒤 숫자가 증가함
2. 이 숫자가 Yogi 개수인지 Box ID인지 사용자가 알 수 없음
3. Esc를 누르자 모든 내용이 사라짐
4. UI가 `YogiBox0` 상태가 됨
5. 그 상태에서 전송하자 .NET 예외가 발생하고 엔진 종료

### 수정 방향

Yogi 개수의 카운터는 이름과 분리하여 표시한다.

Esc가 YogiBox의 내용을 비우고 창을 닫는다.

개별 삭제와 전체 삭제는 명시적인 `×`가 담당한다.

잘못된/빈 YogiBox가 전송 경로에 들어가더라도 엔진이 종료되지 않도록 반드시 유효성 검사를 둔다.

프로젝트를 나오는 경우 YogiBox도 마찬가지로 해제된다.

---

# 17. 채팅과 프로젝트 컨텍스트의 방향

실제 테스트에서 Worker 채팅을 열었을 때 프로젝트가 없는 상태로 채팅 화면이 열렸고 이후 기능이 정상 동작하지 않는 문제가 발생했다.

Helper 쪽에는 프로젝트가 없으면 프로젝트를 열어주는 별도 예외 처리가 있었지만 Worker에는 없었다.

그러나 이 예외 처리 자체가 구조적인 문제를 숨기고 있다.

잘못된 흐름:

```text
채팅을 연다
↓
프로젝트가 없네?
↓
프로젝트를 연다
```

채팅이 프로젝트 생명주기를 역으로 조작하는 **역전파**가 발생해서는 안 된다.

기본 원칙은:

```text
현재 프로젝트 상태가 존재
↓
채팅이 필요하다면 그 상태를 참조
```

이다.

---

# 18. Helper 채팅

Helper는 프로젝트에 종속되지 않는다.

Helper는 전역 기억을 사용하는 지속적인 AI이므로 프로젝트가 하나도 열려 있지 않아도 대화 가능해야 한다.

프로젝트가 없는 경우:

```text
Helper
├ 전역 기억
└ 현재 참조 프로젝트 없음
```

으로 대화한다.

프로젝트가 열려 있다면:

```text
Helper
├ 전역 기억
└ 현재 프로젝트 컨텍스트 참조
```

가 추가된다.

중요한 점은:

```text
Helper 채팅을 열었다
→ 프로젝트 자동 오픈
```

이 일어나지 않는다는 것이다.

Helper는 프로젝트를 참조할 수 있지만 프로젝트에 종속되지 않는다.

---

# 19. Worker 컨텍스트

Worker는 Helper와 다르게 프로젝트 및 Task에 종속된 실행 자원이다.

개념적으로:

```text
Worker
├ Owning Helper
├ Owning Task
└ Project Context
```

를 가진다.

그러나 Worker 채팅이나 Worker 상태를 확인한다는 이유로 프로젝트를 역으로 열어서는 안 된다.

Worker는 이미 자신에게 전달된 프로젝트/Task 컨텍스트 안에서 동작해야 한다.

또한 현재 구조에서는 Worker를 기본 사용자 UI에 직접 노출하지 않는 방향이므로, Worker 채팅 자체도 일반적인 사용자 이동 경로에서는 제거될 예정이다.

---

# 20. 역할별 채팅 성격

최종적으로 채팅은 다음처럼 구분한다.

## Helper Chat

```text
프로젝트 없어도 사용 가능
전역 기억 사용
현재 프로젝트가 있으면 필요에 따라 참조
```

## Project Chat

```text
현재 프로젝트에 종속
프로젝트 내부의 공용 대화
메인 도우미나 인간 사용자는 지속적으로 프로젝트의 대화를 수신
일반 도우미는 본인이 태그될 때 수신
하단 프로젝트 패널에서 사용
```

## Worker Communication

```text
Task / Project 종속
Helper가 관리
기본 사용자 UI에서는 직접 노출하지 않음
```

# 22. 이번 정리의 핵심 원칙

이번 실제 사용 과정에서 드러난 원칙은 다음과 같다.

### 1. 내부 상태를 숨기는 것과 현재 상태를 숨기는 것은 다르다.

사용자는 내부 인증 상태 머신을 몰라도 되지만 `연결 중 / 실패 / 연결됨`은 알아야 한다.

### 2. 사용자가 추론해야 하는 필수 조건을 만들지 않는다.

프로젝트 이름이 필요하면 필수라고 표시한다.

### 3. UI 상태 변화가 정보를 제거해서는 안 된다.

버튼을 눌러도 버튼 이름은 읽혀야 한다.

### 4. Worker는 사용자 관리 대상이 아니다.

사용자는 Helper를 보고, Helper가 Worker를 관리한다.

### 5. 프로젝트 내부 탐색과 프로젝트 자체 관리는 분리한다.

```text
▦ = 프로젝트 내부 탐색
≡ = 프로젝트 자체 관리
```

### 6. YogiBox는 보관물이 아니라 전달 패키지다.

별도 저장소를 만들지 않는다.

### 7. 채팅은 프로젝트 생명주기를 역으로 조작하지 않는다.

Helper는 프로젝트 없이도 대화할 수 있으며, 프로젝트가 있다면 그것을 참조할 뿐이다.

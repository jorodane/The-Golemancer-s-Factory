# Confectory 멀티 작업자 · 첫 구현

여러 작업자가 같은 프로젝트에서 독립적으로 제안하고, 변경된 요소·코드 구간을 비교한 뒤 선택한 변경을 적용한다. 파일이나 작업 범위를 선점하는 Lock은 없다. 이 문서는 [확정 설계](COLLABORATION_SPEC.md)의 27번에 따른 첫 구현의 사용법과 실제 경계를 설명한다.

## 사용 흐름

1. 에디터 AI 연결 설정을 준비하고 게임팩을 연다. 기본 `작업자` 탭의 `AI 작업자 추가`로 캐릭터를 늘린다.
2. 캐릭터의 몸통을 드래그해서 배치한다. `대화 · 작업`으로 해당 AI의 독립 창을 열고 요청한다. 다른 AI에도 동시에 요청할 수 있다.
3. 캐릭터 위 말풍선은 사용자 질문과 AI 답변을 한 Turn으로 표시한다. 좌우 버튼으로 이전 Turn을 볼 수 있고 `대화 로그`는 전체 로컬 기록을 연다. 각 작업자는 모델 선택·취소·빌드 재시도·대화 저장을 따로 가진다.
4. 캐릭터를 선택한 뒤 `Exactly Yogi` 또는 `Look At Yogi`를 사용한다. 선택 대상은 표시되고, 캡처를 시작한 시점의 수신자에게 고정된다. 로컬 AI에는 다음 요청에 첨부한다. 웹 전달은 수신자로 `웹 대화`를 명시했을 때만 기존 첨부 기능을 사용한다. 일반 텍스트 요청은 다른 작업자의 선택·첨부를 상속하지 않는다.
5. 요청이 끝나면 독립 검토창이 열린다. 변경된 요소·구간만 기본 표시하고 주변 내용과 전체 파일은 펼쳐 볼 수 있다. 체크된 부분만 적용한다. 새 파일·등록 파일·이미지 묶음은 일관성을 위해 묶음 전체를 선택한다.
6. 다른 작업자의 변경이 먼저 적용되었으면 현재 파일에 낙관적으로 합친다. XML의 서로 다른 요소, 코드의 겹치지 않는 줄 구간은 합칠 수 있다. 같은 요소, 겹치는 코드, 부모 삭제와 자식 수정은 별도 충돌창에서 선택한다. 선택한 후보의 충돌 구간을 채택하면서 양립 가능한 다른 구간을 보존한다.
7. 결정은 아직 파일 적용이 아니다. 구조화된 Resolution ChangeSet과 수정된 제안이 최종 검토로 돌아온다. 검토 중 원본이 또 바뀌면 적용을 막고 `변경 다시 비교`로 다시 확인한다.

기존 대화는 삭제하지 않는다. `이전 대화 열기`와 기존 대화 목록에서 별도 창으로 열 수 있다. 대화·작업·결정 기록은 이 PC의 프로젝트 상태 폴더에 저장한다. 재시작 시 미완료 작업은 interrupted로 남기고 모델 요청을 자동 재전송하지 않는다. 프로젝트의 대화 파일은 명시적으로 `프로젝트에 대화 저장`을 선택했을 때만 갱신한다.

## 계약과 전파

`PackEngine.Workspace`의 `CollaborationWorkspace`가 동일한 Participant 데이터로 Human, AI, EditorPack, Automation을 다룬다. Talk / Work / Apply 권한은 별개다. 기본 AI는 Talk+Work, 로컬 사용자는 Talk+Work+Apply를 가진다. Windows 호스트의 dispatcher가 짧은 상태 변경과 최종 해시 확인·파일 교체를 수행하고 모델 추론과 프로세스 실행은 비동기적으로 진행한다. 공유 compiler 출력과 DLL generation 교체를 사용하는 빌드·reload 실행은 큐로 직렬화한다. 이 큐는 작업자가 파일을 읽거나 변경안을 만드는 동안의 작업권을 선점하지 않는다.

각 WorkContext는 요청 ID, ParticipantId, BaseRevision, 작업 의도, ReferenceSet, WorkingChanges, IncomingChanges, 수용한 ChangeSet, 해결 조건을 가진다. 단순 읽기는 Read로 기록한다. Depend·ModifyIntent만 변경 전파를 구독하며, 제안한 파일에는 ModifyIntent가 붙는다.

`packengine_collaboration` 도구:

| operation | 의미 |
| --- | --- |
| `state` | 이 작업자의 참조·수신 변경·관련 해결 기록을 조회 |
| `reference` | 선언된 파일에 Read / Observe / Depend / ModifyIntent와 선택적 Target을 기록 |
| `respond` | 수신 ChangeSet에 이유와 PASS / ADAPT / OBJECT를 기록 |
| `discuss` | 본인이 참여한 충돌창에 실제 AI 발언을 기록 |

일반 도구 응답에도 수신 변경 문맥을 넣는다. PASS는 겹치는 변경 또는 실패한 검증 결과와 모순되면 거절한다. ADAPT라는 답변만으로 겹친 변경이 해결됐다고 간주하지 않는다. 실제 원본 비교·초안 갱신과 최종 해시 확인을 거쳐야 한다. 시스템이 구간을 합친 사실과 AI가 말한 판단은 기록에서 구분한다. 실행하지 않은 빌드/검사는 `not-run`이다.

ChangeSet은 작성자·기준 revision·의도·작업·부모·origin·검증 결과를 가진다. 제안 이력과 실제 적용 이력은 별도이며 제외된 변경을 적용한 것으로 기록하지 않는다. Resolution은 후보 스냅샷, 참여자, 대화, 조건, 결정과 resulting ChangeSet을 보존한다. 같은 변경의 중복 알림은 걸러내고 실제 적용 변경만 revision을 올린다.

## 비교 단위

XML은 namespace와 안정적인 id/key/node/property/name/platform 속성으로 요소를 식별한다. 속성·텍스트를 포함한 요소 변경, 요소 추가·삭제를 비교한다. 같은 이름의 식별 불가능한 형제, 순서 변경, 복합 내용은 부모 또는 텍스트 범위로 보수적으로 처리한다. 주석·선언·공백만 바뀐 경우에도 변경을 버리지 않는다. DTD를 실행하지 않는다.

코드는 AST 의미 분석 없이 실제 줄 구간과 공통 원본으로 비교한다. CRLF와 마지막 줄을 보존하고 큰 파일은 메모리 제한이 있는 넓은 구간 비교로 전환한다. XML/코드의 의미적 양립성은 빌드·테스트·계약 검증을 대신하지 않는다. 생성 묶음은 각 실제 경로에 대한 파일 단위 변경으로 전파하고 기존 atomic 적용/복구와 해시 검증을 유지한다.

## 첫 구현과 다음 단계

현재 배포는 한 에디터 프로세스 안의 여러 AI 세션, 로컬 사용자, 에디터팩 제안이 같은 프로토콜을 사용한다. 두 후보는 충돌, 세 후보 이상은 격돌로 표시한다. AI 도구 발언과 실제 사람의 발언을 기록하고, 사람이 발언하거나 후보를 선택하면 참가자로 기록한다. 관전은 참가로 취급하지 않는다. 해결창의 최종 선택은 Apply 권한을 가진 사용자가 한다.

다음 단계는 Scope 인계의 요청·수락(TAKEOVER/YIELD), 확정 Resolution의 후손에 대한 의미적 순환 방지, 검증 근거에 의한 HP 계산·10 Turn 자동 결정·Round 발언, 사람 사이의 네트워크 전송/인증/동기화다. 해당 기능은 이 버전에서 실행된다고 표시하지 않는다. 계보를 이유로 후손의 새로운 실제 충돌을 무조건 숨기지도 않는다.

실제 Windows에서 두 Codex 계정/세션의 동시 응답, 캐릭터 드래그·말풍선·독립 창, Yogi 시각 캡처, SDK 설치 후 작업자별 재시도를 확인해야 한다. Linux의 프로토콜 fixture는 실제 유료 모델 응답이나 GUI 조작의 증거가 아니다.
